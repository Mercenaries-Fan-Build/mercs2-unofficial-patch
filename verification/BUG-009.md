# BUG-009 — `Pg.UnloadLayer` NULL-derefs on a co-op client with no current game state

**Status going in:** `built`. Ships in `unofficial_patch.asi`, source
[`bug_009_unloadlayer_null.c`](../native/src/bug_009_unloadlayer_null.c). See [README](README.md) for
build and install.

A **crash**, and the hardest of the four to reach on purpose — it needs a co-op client in a specific
state. Read the fallback below if you cannot get two machines on.

## The condition, precisely

Three things must hold at once:

1. you are a co-op **CLIENT** (`[0x00DFBD77]` non-zero — the host never hits this);
2. **no game state is current** (`[0x01175C7C]` is NULL);
3. something calls `Pg.UnloadLayer`.

The function tests `Net.IsClient` and then immediately reads `[state + 4]` with nothing between
them, so a NULL state is read at `NULL+4`.

State becomes NULL after an **unrecognised** `Sys.RequestGameState` string — the request is refused
and the current-state pointer is left null. Both refusal paths return `true`, so a caller checking
the return cannot tell a swallowed request from an accepted one, which is how you end up in this
state without noticing.

## Reproduce BEFORE — on the client, over the REPL

```lua
Sys.RequestGameState("this_is_not_a_real_state")   -- returns true, and clears the state
Pg.UnloadLayer("anything")                          -- crash
```

Run it on the **client**. The identical pair on the host is harmless — that asymmetry is the
signature, and it is worth confirming both ways so you know you reproduced *this* bug.

## Expected AFTER

- The same pair on the client returns harmlessly. No crash.
- The pack logs, once per occurrence:
  ```
  BUG-009: refused Pg.UnloadLayer on a client with no game state (would read NULL+4)
  ```
- **Normal co-op layer loading and unloading still works** — the regression that matters. The hook
  intercepts only when *both* conditions hold; a client with a live game state, and the host in any
  state, run the original untouched. Play a co-op contract through a mission transition and confirm
  layers still stream in and out.

## If you cannot get two machines on

The log line is the evidence. It is emitted only on the exact path that would have crashed, so if it
ever appears during ordinary co-op play, the fix caught a real occurrence — and its absence over a
long session is weak evidence the condition is rare, not that the fix is broken.

Do **not** mark this `verified` on the log line alone. Reproducing it once is worth more than any
amount of uneventful play.

## Address corrections

Verified against the target build; two differ from the register:

| | register | actual |
|---|---|---|
| `cmp byte [0x00DFBD77], 0` | `0x005D4E49` | `0x005D4E49` ✓ |
| `je 0x005D4E6C` | `0x005D4E49` | **`0x005D4E53`** — three `push`es sit between cmp and branch |
| `mov eax, [0x01175C7C]` | `0x005D4E55` | `0x005D4E55` ✓ |
| `cmp dword [eax+4], …` | `0x005D4E5A` | `0x005D4E5A` ✓ |

The defect itself is exactly as described. Entry `0x005D4E40`, confirmed via the `Pg` binding-table
slot at `0x00B99364`.
