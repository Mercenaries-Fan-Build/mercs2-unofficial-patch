# BUG-007 — three PDA blip binders dereference NULL

**Status:** ✅ **verified live 2026-08-10** — the AFTER path on all three binders: an out-of-range id
returns harmlessly with the game intact (see end of card). Ships in `unofficial_patch.asi`, source
[`bug_007_pda_blip_null.c`](../native/src/bug_007_pda_blip_null.c). See [README](README.md) for build
and install.

This is a **crash**, not a glitch, and it is the highest-value fix in the pack.

## Reproduce BEFORE — one line, no debugger

Over the REPL, with the fix **disabled** (`BUG_007 = 0` in `unofficial_patch.ini`, then restart):

```lua
_GuiInternal.RemovePdaBlip(-1, "x")
```

**The game crashes.** `id = -1` fails the bounds check, the binder does `xor eax,eax`, control merges,
and `0x005BD139` reads linear address `0x00000010`.

The second argument is irrelevant — its type check happens *after* the fault. The same holds for the
other two:

```lua
_GuiInternal.AddPdaMapBlips(-1, {})    -- faults at 0x005BCEEF
_GuiInternal.UpdatePdaBlip(-1, {})     -- faults at 0x005BD00F
```

**Test all three.** The register and the first validation pass both named only `AddPdaMapBlips`; the
scope is three binders, and a fix verified on one proves nothing about the others.

### The gameplay path

The synthetic `-1` proves the crash. The way a player reaches it is a **stale** id: ids are reused,
and deleting a widget clears its slot while leaving the id in circulation — so a PDA close/reopen
carrying a stale blip id hits an in-range slot holding NULL. Worth exercising if you can, since it is
the second reaching condition and it is the one that happens by itself.

## Expected AFTER

- All three one-liners return harmlessly. No crash, no error.
- **The PDA map still works normally** — this is the regression that matters. The hook only
  intercepts once it has positively established that the original *would* fault; every legitimate
  blip call still runs the original. Open the PDA, take a contract, watch objective markers appear
  and clear. If blips stop showing up, the validation is rejecting valid ids.

## Why it fails towards the original

If the blip-manager chain cannot be resolved — unexpected layout, PDA not yet constructed — the hook
**calls the original anyway** rather than refusing. Refusing on a chain we failed to read would
silently break every blip call in the game, which is a worse outcome than the crash being fixed.

That has a consequence for testing: if the manager cannot be read, the crash comes back rather than
the PDA breaking. So a *successful* run of the three one-liners is real evidence; a crash means the
validation path did not engage, not that the fix is absent.

## Notes on the addresses

Entries confirmed via `_GuiInternal` binding-table slots: `AddPdaMapBlips` `0x005BCE70`,
`UpdatePdaBlip` `0x005BCF90`, `RemovePdaBlip` `0x005BD0C0`. Chain is `[gui+0x68]` → blip manager,
`+0x44` slot array, `+0x4C` slot count, with `gui` at `[0x01175FB0]`.

The array has **zero slack** (`push 0x200`, cap `0x80`), so `id == count` is a real 4-byte heap
over-read whose garbage pointer is then dereferenced. The check treats `id == count` as out of range
rather than trusting whatever it would find there.

## Verified live (2026-08-10)

The AFTER path, exercised over the `lua-bridge` REPL with the **PDA map open** (so the blip manager is
constructed and the validation path engages):

| binder | call | result |
|---|---|---|
| `UpdatePdaBlip` | `_GuiInternal.UpdatePdaBlip(9999)` | returned, game alive |
| `RemovePdaBlip` | `_GuiInternal.RemovePdaBlip(9999)` | returned, game alive |
| `AddPdaMapBlips` | `_GuiInternal.AddPdaMapBlips(9999)` | returned, game alive |

Each call was followed by an `alive` probe (`1+1 → 2`) that came back, confirming the process survived
all three. `id = 9999` is far past the `0x80` slot cap — the out-of-bounds pointer read that CTDs
vanilla — so a harmless return is the fix intercepting, and (per "fails towards the original" above) a
successful run with the manager readable is real evidence the validation engaged.

**Strengthened 2026-08-11** (x32dbg on the verified build, `Mercenaries2.exe` CheckSum `0x00A5438D`):
read the blip-manager chain directly — manager `[gui+0x68]` = `0x1FF07BC0` (non-null), slot array
`[mgr+0x44]` = `0x1F8B4000` (non-null), slot count `[mgr+0x4C]` = **512**. So `id = 9999` is genuinely
`≥ count`: the fix's `WouldFault` guard fires and the hook returns 0 *without* calling the original.
Re-firing `UpdatePdaBlip(9999)` in that same session survived (`alive 4`). This shows the survival is
the intercept doing its job, not the original being coincidentally safe — vanilla would address
`0x1F8B4000 + 9999·4`, ~40 KB past the 512-byte allocation, and deref whatever it read there.

Remaining scope: no fix-off/on restart A/B; and only the **out-of-range** reaching condition was
exercised — the **in-range stale-slot** path (`slots[id] == 0`) was not.
