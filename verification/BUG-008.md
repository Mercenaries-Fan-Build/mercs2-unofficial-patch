# BUG-008 — `Gui.ShowLoadingHints(false)` is a one-way switch

**Status:** ✅ **flag verified live 2026-08-11** — `[gui+0x39]` now writes in both directions
(`true→1`, `false→0`), by direct memory read (see end of card). Still **partial by design** on the
notify — read the scope note below. Source [`bug_008_loading_hints.c`](../native/src/bug_008_loading_hints.c).
See [README](README.md) for build and install.

## Reproduce BEFORE

Over the REPL:

```lua
Gui.ShowLoadingHints(true)
Gui.ShowLoadingHints(false)
```

then load a level. **The hints still show.** The flag `[gui+0x39]` is written in exactly one place
and an explicit `false` branches past it to the epilogue, so the flag can be set and never cleared.

An *absent* argument defaults to **true**, which is part of why this went unnoticed — only an
explicit `false` is broken, and it is the one spelling that looks like it should obviously work.

### Reading the flag directly

More precise than watching the loading screen, if you have a debugger attached: the flag is
`[[0x01175FB0] + 0x39]`. A hardware write watchpoint on it fires on the `true` and omitted calls and
**never** on `false` — that asymmetry *is* the bug, and it is the cleanest before/after evidence.

## Expected AFTER

- The same two calls, then a level load: **hints do not show**.
- `Gui.ShowLoadingHints(true)` still turns them on. The fix touches only the `false` case; `true` and
  absent already worked and must keep working.
- The write watchpoint now fires on `false` too.

## ⚠ Scope — the notify is deliberately NOT forced

The register says a correct build "also needs the notify at `0x005B4C74` made reachable". **This fix
does not do that**, and that is a decision rather than an omission.

Disassembling this build turned up an **undocumented second gate** the register does not mention,
sitting between the flag store and the notify:

```
0x005B4C68  mov  byte ptr [ecx + 0x39], al    ; the flag — what this fix corrects
0x005B4C6B  cmp  byte ptr [0x00DF67F4], 0     ; ⚠ not in the register
0x005B4C72  je   0x005B4C86                   ; -> epilogue, skipping the notify
0x005B4C81  call 0x00608590                   ; the notify
```

So the notify is conditional on a global whose meaning we have not established. Forcing it would
mean firing a subsystem notification under a condition the game deliberately excludes, on a guess.

**What that means for the result:** the flag is what the 8 Lua call sites are actually asking to
change, and it is now correct in both directions. If hints still appear **with the flag confirmed
clear**, that is not this fix failing — it is evidence that the notify matters, and the next step is
identifying `0x00DF67F4` rather than forcing the branch. Record which of the two you saw.

## Verified live (2026-08-11)

Flag `[[0x01175FB0] + 0x39]` read directly via x32dbg on the verified build (`Mercenaries2.exe`,
CheckSum `0x00A5438D`, hooks armed 4/4), toggled over the `lua-bridge` REPL. The gui singleton was
stable at `0x20A9F560` throughout:

| step | `gui+0x39` |
|---|---|
| baseline | `0x00` |
| `Gui.ShowLoadingHints(true)` | `0x01` |
| `Gui.ShowLoadingHints(false)` | `0x00` |

`false` cleared the flag (`1 → 0`) — the fix's whole job, and something the unpatched build cannot do
(the `false` path branches at `je 0x005B4C86` past its only store to `[gui+0x39]`, leaving it `1`).
The flag is now correct in **both** directions, exactly the fix's stated scope.

Not settled here: whether hints visually stop appearing — that also depends on the notify gated behind
the undocumented `0x00DF67F4` (scope note above), deliberately out of scope. No fix-off/on restart A/B
was run; the observed value change against the known vanilla disassembly is conclusive on its own.
