# BUG-006 — the hero-swap save/restore hands back more than it was given

**Status:** ✅ **verified live 2026-08-10** — both halves confirmed against the running VM (see the
end of this card). Ships as
[`bug_006_heroswap_save_restore.lua`](../src/lua/bug_006_heroswap_save_restore.lua) → `mrxplayer`.

Two defects, one file — both live in `SaveSingleton`, and an append can only redefine it once:

| | defect | fix |
|---|---|---|
| (a) | clip ammo never saved → magazine returns FULL | save it as a 3rd tuple element, restore it in the existing `ObjectHibernation` callback |
| (b) | `nHealth` saves `GetMaxHealth` → hero returns at FULL HEALTH | save `Object.GetHealth` instead |

## Settled during the build: this is pure T2, no exe patch

The register flagged this as possibly needing a new binding, because **no shipped script anywhere in
either Lua corpus calls a clip-ammo function**. That turned out to be a fact about the scripts, not
about the engine.

The retail `Weapon` table (`0x00B98860`, 9 entries, terminator `0x00B988A8`) contains both:

| binding | VA |
|---|---|
| `Weapon.GetClipAmmo` | `0x005EA5F0` |
| `Weapon.SetClipAmmo` | `0x005EA520` |

Both resolve `RuntimeWeapon` (`0x017BEC08`, stride `0x34`) and touch `+0x30` — the sibling field to
reserve ammo at `+0x24`. The game shipped them and never called them.

## Confirm the bindings exist — 10 seconds, before anything else

Over the `lua-bridge` REPL (`127.0.0.1:27050`):

```lua
local w = Human.Inventory.GetPrimaryWeapon(Player.GetCharacter(Player.GetLocalPlayer()))
print(Weapon.GetClipAmmo(w), Weapon.GetMaxClipAmmo(w), Weapon.GetReserveAmmo(w))
Weapon.SetClipAmmo(w, 3)   -- the HUD clip counter should drop to 3
```

If `GetClipAmmo` returns nil for a live carried weapon, the container resolve is wrong and this fix
cannot work as written — stop and say so. If `SetClipAmmo(w, 3)` does not move the HUD, `+0x30` is
not the field the HUD reads.

## Reproduce BEFORE

1. Take a weapon with a clip — a rifle, not a grenade.
2. Fire until the magazine is visibly part-empty (say 7/30). Leave reserve ammo well above zero, so
   you can tell a refill from a reload.
3. Swap heroes.
4. **The magazine comes back full.** Reserve is carried over correctly, which is what makes this easy
   to miss.

## Expected AFTER

- Same steps: the magazine comes back at **7/30**, reserve unchanged.
- **Grenades and C4 still work and no script error appears.** This is the regression that matters:
  `Get/SetClipAmmo` **raise** on thrown and trigger weapons (`test byte [rec+0x26], 3` in both
  bodies), and those are in the normal loadout. Both calls are `pcall`-wrapped for exactly this
  reason. A red script error on swap means the guard is not doing its job.
- An **old save** (written before the patch) still restores: the saved tuple grew from 2 elements to
  3, so a pre-patch save simply has no `[3]` and behaves exactly as it does today. Load one and
  confirm the swap still restores reserve.

## (b) The health half — reproduce and expect

**Before:** take damage (say down to a third), swap heroes → **you come back at full health.**

**After:** you come back at the health you left with.

The reference is exact rather than inferred: `Object.GetHealth` is in the retail `Object` table
(`0x00B99608`, 87 entries) beside `SetHealth` and `GetMaxHealth`, has **49 shipped call sites**, and
`hero.lua:125-137` uses all three together — which pins that they share one scale, so what
`GetHealth` returns is exactly what `SetHealth` takes. That same site guards
`if not nCurrentHealth then return end`, so `GetHealth` can return **nil**; an unresolvable character
therefore falls back to retail's `GetMaxHealth` rather than writing nil.

⚠ **This is a deliberate behaviour change.** Hero swapping stops being a free full heal, which some
players may have been leaning on. If that turns out to be load-bearing, revert the one line — the
ammo half of the file does not depend on it.

## Verified live (2026-08-10)

Confirmed against the running game over the `lua-bridge` REPL by inspecting what
`MrxPlayer.SaveSingleton()` actually captures — it is read-only, so the probe mutates nothing.
(`MrxPlayer` is reached with `import("MrxPlayer")`; the `Mrx*` module tables are not `_G` globals.)

**Clip ammo — the registered defect.** Four items equipped:

```
maxTupleLen=3  equip=4  withClip=2  clipSample=93
```

- `maxTupleLen=3` — the saved weapon tuples now carry the 3rd element; vanilla saved a 2-tuple
  `{parent, reserve}`. Clip ammo is in the save data.
- `withClip=2` of `4`, `clipSample=93` — two weapons captured a real clip value; the other two
  captured `nil` and were skipped. That is the `pcall(Weapon.GetClipAmmo)` guard working — grenades /
  C4 / melee raise on that binding and are correctly excluded. Happy path *and* guard confirmed.

**Health — the adjacent defect.** Taken deliberately at part health (a full-health sample can't tell
`GetHealth` from the old `GetMaxHealth`):

```
curHP=5.556  maxHP=120  savedHealth=5.556   → == CURRENT, not MAX
```

Saved health equals **current** (5.556), not **max** (120). Vanilla saved `GetMaxHealth` (→ a free
full heal on swap); the fix saves `GetHealth`.

Scope: this confirms the **save** side (what gets captured). The restore side re-applies both counters
in the existing `ObjectHibernation` callback; the full save→swap→restore round-trip was not exercised
live here.
