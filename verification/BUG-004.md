# BUG-004 — five profile setters never dirty the profile, so their changes are not autosaved

**Status going in:** `built`. Ships in `unofficial_patch.asi`, source
[`bug_004_autosave_dirty.c`](../native/src/bug_004_autosave_dirty.c). See
[README](README.md) for build and install.

## ★ Do this first — the fix may be inert, and one log line settles it

The autosave has **two** gates, ANDed: the dirty byte at `profile+0x11` (what this fix sets) and a
second at `profile+0x25F`. The only writer of `+0x25F` anywhere in the image is a profile
clear/init that sets it to **zero**. If nothing sets it non-zero at runtime, dirtying `+0x11` changes
nothing and this fix does nothing.

That cannot be settled statically — the save path runs through a SecuROM thunk — so the module logs
the value the first time it dirties the profile. Play until any profile value changes, then read
`scripts/unofficial_patch.log`:

```
BUG-004: dirtied the profile; second autosave gate [+0x25F] = 1
```

- **`= 1`** (or any non-zero) — the second gate is open at runtime. The fix should work; carry on
  with the repro below.
- **`= 0  <-- ZERO: autosave is still gated shut, this fix is INERT`** — stop. The fix is correct and
  irrelevant, and the entry needs a second patch (force `+0x25F` non-zero, or neutralise the `je` at
  `0x0061489E`). **Report the line rather than assuming the fix failed** — it is doing exactly what
  it was written to do.
- **No such line at all** — nothing ever changed a profile field through the five hooked setters
  during that session. Try the repro below, which forces one.

## Reproduce BEFORE

The defect only shows when a profile field changes **alone**, with nothing else touched — any other
dirtying change (fuel, a profile upgrade, `AddCash`) masks it, which is why this went unnoticed.

Easiest via the REPL, because it changes exactly one thing:

```lua
Player.SetCash(Player.GetLocalPlayer(), 1234567)
```

⚠ **Do not pass a second argument.** `SetCash` and `SetFuel` take an undocumented optional boolean
that **suppresses the write entirely** — `SetCash(n, true)` silently does nothing, and would look
like this fix failing.

Then: let the game autosave (or trigger one), quit, relaunch, reload. **The cash is back to its old
value.** The same holds for fuel capacity, profile character, profile costume, and the
available-costume roster.

## Expected AFTER

Same steps: the value survives the reload.

The regression that matters is the opposite one — **the game must not save constantly.** The hook
compares the field before and after and dirties only on a real change, exactly as `SetFuel` and
`SetProfileUpgrade` do. Setting cash to the value it already holds, or calling `SetCash(n, true)`
where the write is suppressed, must **not** mark the profile dirty. If the game starts autosaving on
every frame, that comparison is what to look at.

## Where the addresses came from

The register cites the *store* inside each body (`0x005DF4FE`, `0x005DF778`, `0x005DF828`,
`0x005DF978`, `0x005DFB98`). Those are not hookable. The entries below are the `Player`
binding-table slots, each the only pointer to that function in the image:

| setter | entry | field |
|---|---|---|
| `SetCash` | `0x005DF480` | `+0x2C` dword |
| `SetFuelCapacity` | `0x005DF720` | `+0x30C` dword |
| `SetProfileCharacter` | `0x005DF7D0` | `+0x61` byte |
| `SetProfileCostume` | `0x005DF920` | `+0x63` byte |
| `SetAvailableCostumes` | `0x005DFB40` | `+0x25E` byte |

`SetFuel` (`0x005DF64E`), `SetProfileUpgrade` (`0x005DF8C3`), `AddCash` (`0x005DF56C`) and `AddFuel`
(`0x005DF6D8`) all do dirty correctly — which is what makes the five an oversight rather than a
design decision.
