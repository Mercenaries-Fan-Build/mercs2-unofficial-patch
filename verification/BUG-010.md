# BUG-010 — PDA support quick-slot — **NOT A BUG. Nothing ships.**

**Disposition: downgraded from `confirmed` to cut content / dead code.** The support quick-slot
feature works. `EnableQuickSlot` is an orphaned *parallel* implementation that was cut before ship,
not a working feature that broke.

Recorded here rather than dropped, so nobody re-derives it — and because the proposed one-line
repair is not merely insufficient, it is **actively wrong**.

## Why the one-liner must not ship

The proposal was to point `_LTIupdateSupportQuickSlot` at `EnableQuickSlot(sParm)`. Three
independent reasons not to:

**1. The feature already works, by another path.** The live chain is fully wired:

```
SUPPORT.gfx slots 1-3  →  FSCommand:equip  →  mrxguipda.lua:1536 _HandleEquipEvent (:1091)
  →  tEquippedSupport[nSlot] / tEquippedSupportIcons[nSlot]
  →  HUD wheel: mrxguihudsupportmenu.lua:155 Trigger → :622 TriggerItem → Commence(true)
```

`_HandleEquipEvent` parses `"<slot>, <id>"`, resolves `tSupportIdIndex[sId]`, and writes the live
state. Denial reasons work too (`equipFailed` → `_ShowUnusableSupportMessage`, `:1069`).

**2. The two implementations use disjoint state, and the dead one's is never initialized.** Counted
across the whole corpus:

| state | sites | where |
|---|---:|---|
| `tEquippedSupport` (live, 3-slot, net-synced) | **35** | throughout the PDA + HUD |
| `sCurrentlyEquippedSupport` (dead, 1-slot) | **5** | all inside `EnableQuickSlot` itself, `:1870-1882` |

Nothing initializes `sCurrentlyEquippedSupport` in the widget-setup block, and nothing outside
`EnableQuickSlot` ever reads it.

**3. ★ It would DEPLOY the support, not equip it.** `EnableQuickSlot:1885-1891` duplicates
`TriggerItem`'s shape — `Create` / `SetSupportName` / `SetFuelCost` / `SetCashCost` / `Commence`.
And `mrxsupport.lua:228-235`:

```lua
function Commence(self, bFireImmediately)
  if "table" ~= type(self.oDesignator) then
    ...
    self:BeginSupportSequence()   -- ← fires OUTRIGHT, bFireImmediately not consulted
    return true
  end
```

So for any support without a designator, wiring the handler would **call in the airstrike the moment
the player selected it**. Note also that `EnableQuickSlot` calls `Commence()` where `TriggerItem`
calls `Commence(true)` — a difference that only matters on the designator branch, and we have no
evidence which was intended. The repair is a guess about semantics, not only about reachability.

## A dead registration is not evidence of breakage

`_FinishLoad:1537` also registers `unequip`. `FSCommand:unequip` appears in **zero** shipped movies,
and `_HandleUnequipEvent` (`:1136-1137`) is an **empty function**. Unraised handler registrations are
a pre-existing, benign pattern in this file.

## ⚠ The recorded evidence for this entry could not be reproduced as written

Two corrections that matter beyond BUG-010:

**The `.gfx` extraction recipe in the record produces silent false negatives.** A movie entry is not
`zlib.decompress(bytes[8:])`. It is a 40-byte `UCFX` engine prefix, then `CFX` + `0x08` + a u32
uncompressed length, then the zlib stream — inflate at `find(b"CFX\x08", 4) + 8`. Run with the
recorded method, **every token returns zero, including positive controls.** Any re-run of that
validation "confirms" its claim vacuously. The register's cited `output/gfx_movies/` no longer
exists, so this was not otherwise catchable.

Re-derived correctly — 83 movies (vz 64 + shell 16 + Loading 3 + English 0, matching
`aset_export.csv`), **80 `CFX`/zlib and 3 uncompressed `GFX`** searched as plaintext — the negative
holds: 0 hits for `LTIupdateSupportQuickSlot`, `updateSupportQuickSlot`, `EnableQuickSlot`, or any
casing of `quickslot`. This time with positive controls that fire (`FSCommand:equip` → `SUPPORT`,
`store`; `FSCommand:closePDA` → `topbar`, `Statistics`, `Garage`), which is what makes the zero
meaningful.

**The handler is attached to `topbar.gfx`, not `Map.gfx`.** `mrxguipda.lua:1436-1437` sets
`oMapFlash.CustomData.sFile = "topbar"`. `Map.gfx` carries no support code at all.

## What a real fix would have needed — and why it is not a fix-pack item

Three ends, of which we can touch one:

1. **Flash — blocking.** Author AS2 into `SUPPORT.gfx`/`topbar.gfx` to raise the event. There is no
   `.gfx` write path: `tools/mercs2-tools-gfxforge/` is an unchecked-out empty submodule and is in
   any case an author-from-scratch emitter with **no importer and no injector**. Retail movies cannot
   be decompiled, modified and recompiled.
2. **Engine.** The forwarder `LTILibName.LTIupdateSupportQuickSlot` (table `0x00B99C78` slot #50) is
   the shared retail-stripped stub `0x006D5640` = `33 c0 c3` (`xor eax,eax; ret`). It is
   `/OPT:ICF`-folded with **61 other bindings**, so it cannot be edited in place without breaking
   `Ai`/`Junk`/`Sound`/`Debug`/`print`; it would need a new body plus a table-slot repoint. And we do
   not know what it was supposed to do — `LTI` is a PC-port-only namespace, absent from the entire
   DLC corpus, so the console builds give no oracle.
3. **Lua.** The one-liner. Necessary, insufficient, and of unknown correctness.

That is a content-authoring project, not a bug fix.

## What would reopen this

An in-game repro showing a PDA support-slot interaction that produces no effect. The static evidence
predicts none exists: every slot interaction the shipped UI offers routes through `equip`, which is
live.
