# BUG-005 — SetAllWeapons drops weapons / re-classes primaries on a hero swap

**Status:** parked (not shipped) → **observation obtained 2026-08-11**. The runtime capture that a
from-static fix was blocked on now exists (below). The fix itself is **not yet written or verified** —
it ships when it is. Tracked in the not-shipped block of
[`native/src/fixpack.h`](../native/src/fixpack.h).

## The defect

The applier `FUN_006F8EF0` (`0x006F8EF0`) mis-distributes weapons across a hero swap. The control-flow
defect is confirmed: `cmp ebp,4 / jge 0x005BF337` jumps INTO the secondary-store block. The register's
"2 primary + 2 secondary" does not hold for this build — both caps are `cmp reg,4` and both buckets are
4 dwords wide.

## Why it was parked

`FUN_006F8EF0` takes 1 character + 4 weapon slots, but which caller frame slot maps to which applier
parameter was ambiguous under static analysis — the call site (`0x005BF390`..`0x005BF3B2`) reuses stack
slots heavily and shares one `add esp,0x10` cleanup, so a from-static rewrite would be guessing which
weapon lands in which slot. `fixpack.h` parked it on one observation:
**the 4 slot values read at `0x005BF3A9` during a real hero swap.**

## Observation obtained (2026-08-11) — x32dbg on the verified build

Breakpoint at `0x005BF3A9` (the `call FUN_006F8EF0`), captured across **two** real hero swaps, then
correlated to the resulting inventory over the `lua-bridge` REPL (`tostring(guid)` prints the raw
handle; per-slot ammo identifies the weapon).

The call, as the applier receives it:

```
FUN_006F8EF0(character, stackA, stackB, eax, ecx)
  character = esi         (tag 0x4… instance guid)
  stackA    = [esp+0x34]  \
  stackB    = [esp+0x38]   \  four weapon-parent (type) guids, tag 0x8…
  eax       = [esp+0x48]   /
  ecx       = [esp+0x50]  /
```

**Swap 2** (character `0x40005A77`), guids resolved to weapons via inventory slot + ammo:

| applier arg | frame slot | guid | → inventory slot | weapon (by ammo) |
|---|---|---|---|---|
| `eax` | `[esp+0x48]` | `0x80006ED0` | 1 | Fuel-air RPG (clip 1 / res 4) |
| `ecx` | `[esp+0x50]` | `0x8000569E` | 2 | Light MG (clip 100 / res 6) |
| stackA | `[esp+0x34]` | `0x80005FD3` | 3 | C4 (res 243) |
| stackB | `[esp+0x38]` | `0x80002331` | 4 | Grenades (res 9) |

**Resolved mapping: the two register args (`eax`, `ecx`) fill inventory slots 1 & 2; the two stack
args fill slots 3 & 4.**

**Swap 1** (character `0x4000DD99`) corroborates it independently:

```
stackA / stackB = 0x80005FD3 / 0x80002331   (identical to swap 2 — C4 + grenades, the defaults every merc carries)
eax             = 0x8000436F                (differs — that hero's primary)
ecx             = 0x00000000                (that hero's 4th combat slot was empty)
```

Slots 3 & 4 held the *same* two guids for both heroes (the default C4 + grenades) while slots 1 & 2
tracked each hero's distinct loadout — exactly consistent with the mapping.

## What remains

The blocker is cleared: a fix can reconstruct the `SetAllWeapons` call knowing `eax`→slot 1,
`ecx`→slot 2, stackA→slot 3, stackB→slot 4. Still to do — design a detour that corrects the
`cmp ebp,4 / jge 0x005BF337` mis-branch without dropping or re-classing a weapon, build it as
`bug_005_*.c`, and verify against a real swap using the same breakpoint + inventory-correlation method
used to obtain this observation.
