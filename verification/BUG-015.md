# BUG-015 — the HQ stockpile is saved but never restored

**Status:** built — not yet observed in-game. Ships as
[`bug_015_stockpile_restore.lua`](../src/lua/bug_015_stockpile_restore.lua) → `wifpmcinterior`.

## The defect

`wifpmcinterior.lua` (decompiled retail, `vz` scripts block):

| line | code |
|---|---|
| `:1624-1628` | `SaveSingleton` returns `{ bUnlocked = …, tStockpileQty = _tStockpileQty, tIntroduced = … }` |
| `:1636-1638` | `LoadSingleton`: `if tSaveData.tSupportQty then _tStockpileQty = tSaveData.tStockpileQty end` |

The guard tests `tSupportQty`, a key nothing in the shipped Lua writes: the only occurrence of
`tSupportQty` in the base-game corpus is that guard. So `_tStockpileQty` keeps its module-load value,
`{}` (`:243`), after every load. The Xbox 360 script has the same guard, so this is not a PC-port
defect.

## What it costs the player

`_tStockpileQty` is the HQ stockpile's **high-water mark**, one entry per category of `_tStockpile`
(`:244`: `money` and twelve support items). `_UpdateStockpile` (`:1541-1597`), which runs each time
the HQ interior finishes loading (`_Kickoff`, `:522-536`, once the hero has teleported in and the
briefing assets are loaded), shows each category at the larger of the
current quantity and the mark, and raises the mark (`:1555-1563`). `_SetStockpileCategoryQty`
(`:1599-1614`) then hides each pile mesh `pmcoutpost_stockpile_<category> <i>` whose threshold is above
that number.

So within one session the HQ piles never shrink: spend support and the piles still show the most you
had. After a load the mark is empty, and the piles drop to what you hold now.

The real stock is unaffected. Support and cash counts come back through `MrxPmc.LoadSingleton` and
`MrxSupportData.LoadSingleton` (`xQ!L.lua:794-795`). Only the HQ display is lost.

The restore runs before the HQ is entered on load: `_GameplaySetup_LoadWorldState` calls
`WifPmcInterior.LoadSingleton` (`xQ!L.lua:799`), and that chain reaches `WifPmcInterior.Enter`
(`:891`, by way of `:850` → `:853` → `:858`). So the first HQ view after a load is already corrected.

## The fix

The appended `LoadSingleton` is retail's body, `:1631-1644`, with the guard reading `tStockpileQty`,
the key `SaveSingleton` writes. Nothing else changes.

- **No save-format change.** Retail has always written `tStockpileQty`, so saves made before the patch
  restore too. Read from save bytes (`mercs2_probe save-dump`, the eight retail fixtures in
  `mercs2_formats/fixtures/saves`): every `tPmcInteriorData` carries `tStockpileQty`, either empty
  (`auto_634304EA`) or all 13 `_tStockpile` categories as numbers (`auto_6A447BF8`, all 0;
  `Mattias Nilsson_6A0E523C`, e.g. `tankbuster = 94`, `money = 342479104`).
- **What a restored mark covers.** Retail cleared the mark on every load, so a save made before the
  patch holds the peak reached since the last load before that save, not a lifetime peak.

## Proven on the bytecode, without the game

`mercs2_probe stockpile-restore` (the `wad_simulator` workspace) reads the `wifpmcinterior` script
asset out of a WAD and runs it in the exact Lua 5.1.5 VM (`mercs2_luac`, the game's dialect). It stubs
`import`, runs the module, calls `LoadSingleton` with a save's `tPmcInteriorData.tStockpileQty` as
saved, then runs `_UpdateStockpile(false)` with the player holding nothing and records what each
category is shown at:

```sh
mercs2_probe stockpile-restore "<wad_simulator>/crates/mercs2_formats/fixtures/saves/Mattias Nilsson_6A0E523C.profile" \
  --expect restored --wad <qm build out>/mercs2-unofficial-patch.wad
```

Exit 0 when the HQ shows what `--expect` says, 1 when it does not, 2 when it could not run. Run on
2026-11-12 against the `Mattias Nilsson_6A0E523C` fixture:

| entry | HQ shows | exit |
|---|---|---|
| retail `vz.wad` (sha256 `a67ada8b…c011`) | all 13 categories at 0: the bug, reproduced | 0 (expected `dropped`) |
| built overlay (sha256 `62a79695…d3be`) | all 13 at the saved mark (`tankbuster` 94, `money` 342479104, …) | 0 (expected `restored`) |
| retail, expecting `restored` (negative control) | all at 0 | 1 |
| overlay, expecting `dropped` (negative control) | the saved mark | 1 |

The rest of the overlay's `scripts_vz` block is carried unchanged: `vz`, `wifpmcgarage`,
`wifmissionflow`, `pmccon003` and `jetcon001` extract byte-identical (sha256) from both WADs, and the
two `wifpmcinterior` entries' INFO and DEPS are identical; only the BINN size differs.

## Confirm on the live VM — 10 seconds

Over the `lua-bridge` REPL (`127.0.0.1:27050`), in single player:

```lua
local m = import("WifPmcInterior")
local tSaved = m._tStockpileQty
m.LoadSingleton({ tStockpileQty = { artillery = 9 } })
print(m._tStockpileQty.artillery)   -- 9 with the fix; without it, whatever the mark already held
m.LoadSingleton({ tStockpileQty = tSaved })   -- put the live mark back
```

With no `bUnlocked` and no `tIntroduced` in the table, `LoadSingleton` touches nothing but the
stockpile mark.

## Reproduce BEFORE

1. Stock a support category past its top pile threshold (`_tStockpile`, e.g. `bunkerbuster`
   `{1, 2, 4}`: hold 4 or more), and visit the HQ. Every pile of that category is visible.
2. Spend it down below its middle threshold (bunkerbuster: to 1), and visit the HQ again in the same
   session. **The piles are all still visible.** That is the high-water mark working.
3. Save, quit to the menu, and load that save. Visit the HQ.
4. **The piles have dropped to the current quantity** (bunkerbuster at 1: only pile 1).

## Expected AFTER

- Same steps: after the load the HQ shows the same piles as at step 2.
- A new game (no save) is unchanged: the mark starts empty, as in retail.
- **Overreach would be:** piles showing more than the session's peak before the save, or any
  change to the support or cash counts themselves (the PDA, the shop, the HUD support menu). The fix
  writes only `_tStockpileQty`.
- Co-op: `LoadSingleton` runs only on the host or in single player (`xQ!L.lua:784`). A client receives
  the host's piles through `NETEVENT_UPDATESTOCKPILE`, which `_OnPlayerJoined` sends from
  `_UpdateStockpile(true)` (`:1646-1647`). This is read from the code and has not been watched.
